## ステップ 1. 停留所順のファイルを同梱し、新しい日付なら差し替えられるようにする

同梱するのは時刻表の全部ではない。路線と方向ごとの停留所の名前と座標だけです。

ファイルは `flutter/assets/stop_order.json`。`pubspec.yaml` の assets に加える。形は次のとおり。

```json
{
  "updated": "2024-06-04",
  "routes": [
    {
      "ref": "E05",
      "from": "Khu đô thị Smart City",
      "to": "Long Biên",
      "stops": [
        {"name": "Điểm đỗ xe buýt Smart City", "latitude": 21.00481, "longitude": 105.75452}
      ]
    }
  ]
}
```

`updated` は `YYYY-MM-DD`。`routes` は、系統と方向（`from` → `to`）ごとに停留所順が 1 本。同じ系統の往復は 2 本。

中身は、取れるならハノイの GTFS（TUMI Datahub の Hanoi Midday、`hanoi_gtfs_md.zip`、出典は World Bank の Hanoi GTFS）から、系統・方向ごとに代表 1 便の停留所順だけを抜いて作る。全便の時刻、営業日、形状は入れない。圧縮前で 1MB を超えないこと。ダウンロードできなければ、全市を創作して埋めない。取れた分だけでファイルを作り、完了報告に、何系統入ったかと、取れなかった理由を書く。

実行時に使うファイルは、同梱と、設定の更新で保存したファイルのうち、`updated` が新しい方。更新で保存するのはアプリの文書領域で、同梱ファイルは書き換えない。

更新の URL は `StopOrderSource.updateUrl` の 1 定数だけにする。今は空文字。空のとき、取得に失敗したとき、JSON として読めないとき、`updated` が今使っているファイルと同じか古いときは、今のファイルのままにする。新しいときだけ差し替える。この GET に位置情報は付けない。同意のスイッチとは独立で、押したときだけ取りにいく。

設定の「データ」で、路線の「更新」の直下に「停留所順を更新」を置く。副文に、今使っているファイルの `updated` と、それが同梱か取得かを出す。押したあとの結果は、その行の下に 1 行で出す。

- 新しい日付を取った: その日付
- 同じか古い: 今の日付のまま
- URL が空、または失敗: 取れなかったこと。今のファイルは残る

テスト: 古い `updated` では差し替わらない。新しい `updated` では、その後の照合が新しいファイルを見る。壊れた JSON では今のファイルのまま。

## ステップ 2. 公式の順と OSM の停留所を、自信があるときだけ対応させる

系統は `ref` で対応させる。`E05` と `05` は別。方向は、公式の停留所の座標が OSM の停留所にどれだけ重なるかで選ぶ。`from` / `to` の文字列が違っても、重なりが多い方を使う。往復どちらも重なりが同程度なら、その路線は対応できなかったものとする。

停留所の対応:

- 名前は、大文字小文字と前後の空白を無視し、ベトナム語のダイアクリティカルを外して比べる。
- 公式の 1 件と OSM の 1 件は、名前が似ていて（正規化したものが一致するか、短い方が長い方に含まれる）、座標が 150m 以内のときだけ組にする。
- 1 件が複数に当たるときは、距離が近い組を 1 つだけ残す。同じ OSM の停留所を二度使わない。
- 対応した組が 4 件未満、または OSM 側と公式側の少ない方の半分未満なら、自信なし。その路線は変えない。
- 対応した組を公式の順に見たとき、線の上で 1km 以上戻る組が 1 つでもあれば、方向違いとみなして変えない。線は、その `RouteRecord` のポリラインをメンバー順に繋いだもの。`StopOrderRepair` と同じ測り方でよい。

並べた結果:

- 対応した OSM の停留所を、公式の順に置く。
- 対応しなかった OSM の停留所は消さない。線の上の位置が、前後の対応済み停留所のあいだに入るものは、そのあいだに線の順で差し込む。先頭より前、末尾より後ろも同じ。
- 公式にしか無い停留所は足さない。

この結果を、その `relationId` の停留所 ID の順として覚える。カタログのファイル自体は書き換えない。プランナー、経路地図、路線図、− ＋ は、覚えた順がある路線ではその順の `stops` を見る。

覚えた ID が、今の路線の停留所に 1 つでも無くなっていたら、その路線の記憶は捨てて OSM の並びに戻す。路線データを更新したあとに ID が変わる場合がこれです。

テスト:

- 公式の順が Indochina Tower、PiCo、79 Xuân Thủy で、OSM のリストでは PiCo が末尾。対応できたときは、PiCo が Indochina Tower と 79 Xuân Thủy の間に来る。
- 対応が 3 件以下、または半分未満の路線は、順も記憶も変えない。
- 対応した組が線の上で 1km 以上戻るときは変えない。
- 覚えた ID が路線から消えたら、その記憶は無くなり、OSM の順に戻る。
- 対応しなかった OSM の停留所が、線の上で 2 つの対応済み停留所のあいだにあるとき、そのあいだに残る。

## ステップ 3. 路線図で、今見ている路線だけ直す

経路地図（乗車中の行の `AlightStepper` の直下）と、路線図（開いている路線の情報の直下。乗車中でステッパーが出ているときはその直下）に出す。

今の表示順と公式の順を、ステップ 2 で比べる。

- 自信を持って違いがある: 「公式の停留所順と違います」。タップでシートを開く。
- すでにこの路線へ公式の順を適用している: 「公式の順を使っています」。タップでシートを開く。
- 一致している、または自信がない: 何も出さない。

違いがあるシート:

- 停留所の全文リストは出さない。今の降車停の前後だけ。降車停が無いときは、最初に順が違う箇所の前後だけ。
- 例: 「79 Xuân Thủy の手前は、今は Indochina Tower。公式では PiCo。」
- ボタンは「この路線を公式の順にする」だけ。押すとシートを閉じ、その路線の停留所順を公式の順に切り替える。ピンと − ＋ の隣は、すぐその順になる。

適用済みのシート:

- 同じ前後の説明を、公式の順として出す。
- ボタンは「元に戻す」だけ。押すとその路線の記憶を消し、OSM の並びに戻る。

テストはウィジェットでなくてよい。ステップ 2 の結果で、違いがある路線ではヒント用の文が作れ、一致した路線ではヒントが無いこと。

## ステップ 4. 設定で、時間があるときに全路線を点検する

「停留所順を更新」の直下に「停留所順を点検」を置く。押したときはまだ適用しない。照合結果をシートで出す。

- 直せる路線: 自信を持って違いがある系統の数
- そのままにする路線: 自信がなかった系統の数と、その `ref` を 1 行に 1 系統
- すでに公式の順で、違いが無い系統は数に入れない

ボタンは「直せる路線を公式の順にする」。直せる路線が 0 のときは押せない。押すと、直せる路線だけステップ 2 の順を記憶し、シートを閉じる。そのままにする路線は変えない。

適用したあとは、その路線の路線図の「公式の停留所順と違います」は出さない。「公式の順を使っています」になる。

テスト: 直せる 1 系統と、自信がない 1 系統があるとき、適用すると前者の記憶だけ残り、後者の停留所順は元のまま。
